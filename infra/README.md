# Test infrastructure — GHSA-frr6-h895-5pxp (TLS cert-trust bypass)

This directory documents and automates the lab used to safely test the
behavior described in
[GHSA-frr6-h895-5pxp](https://github.com/dart-lang/sdk/security/advisories/GHSA-frr6-h895-5pxp):
`dart:io` validates TLS chains with its own bundled BoringSSL and, in
versions prior to 3.47.8/Dart 3.13.7, didn't honor distrust decisions the
operating system applies to specific CAs (such as the blocklist applied
to the compromised eMudhra intermediates).

**Lab layout:** this folder (`infra/`) sits **outside** the target
Flutter project (`../tls_mitm_poc`), on purpose — it represents the
"attacker" side (forged CA + interceptor proxy), separate from the
"victim" app. The two only talk over the network (via proxy), never
through a code import or build dependency.

## ⚠️ Read before running anything

- **Only use this against infrastructure you control** — your own test
  CA, your own proxy, your own test environment. Never point it at
  production or third-party services.
- **We don't use the real compromised certificates.** They've already
  been publicly revoked/blocked, and nobody outside the attacker has
  their private key — meaning they couldn't be used to forge anything
  even if we wanted to. Instead, we generate our *own* root +
  intermediate CA, which reproduce the **structure** of the problem
  (root still publicly trusted, intermediate distrusted by the OS)
  without relying on any compromised material.
- **Honest limitation:** the lab confirms the generic root cause —
  *"dart:io's default validation doesn't consult the OS's trust
  decision for a specific CA"* — using a CA under our control. It's not
  guaranteed to reproduce byte-for-byte the exact blocklist mechanism
  vendors applied to the real eMudhra intermediates (that detail isn't
  public). The article documents this: the goal is to demonstrate the
  class of flaw, not replicate the original incident.

## The real fix mechanism (confirmed by reading the source)

Research done against public code (without touching any private key):

- The fix is **not in `dart-lang/sdk`**. Commit
  [`ecb2c83`](https://github.com/dart-lang/sdk/commit/ecb2c835161a7ec2e106d961b2eeda6fde8666f8)
  only bumps the vendored BoringSSL revision (via `DEPS`), from
  `2e508c973d63` to `c7eb007fd106`. The blocking mechanism itself lives
  in BoringSSL.
- In BoringSSL, commit
  [`dd68207`](https://boringssl.googlesource.com/boringssl.git/+/dd682072baab8029a83347e639d056c03e48d7e0)
  ("Block a handful of intermediate certificates", David Benjamin,
  2026-10-20) adds, in **two files** (`crypto/x509/x509_vfy.cc` and
  `pki/verify_certificate_chain.cc`), an identical array:
  ```c
  static const uint8_t kBlockList[][32] = { /* 8 entries */ };
  ```
  Each entry is a **SHA-256 hash of the SubjectPublicKeyInfo (SPKI)** —
  i.e. of the public key, not the whole certificate (a more robust
  technique: the same key can be re-encoded into different certificates
  with different fingerprints, but the SPKI hash doesn't change). In
  `x509_vfy.cc`, a new function `check_blocklist(X509_STORE_CTX *ctx)`
  walks each certificate in the chain (`ctx->chain`), recomputes the
  SPKI hash, and compares it byte-for-byte against the 8 entries; on a
  match, it sets `ctx->error = X509_V_ERR_CERT_REVOKED`.
- Separately, commit
  [`a9e26a2`](https://github.com/dart-lang/sdk/commit/a9e26a21af316358c9801681364404ea6e68c767)
  makes `dart:io`, on Android 14+, load system roots from the updatable
  Conscrypt APEX module (`/apex/com.android.conscrypt/cacerts`) instead
  of the old static store — a parallel fix about *how* Android updates
  roots, not about the blocklist itself.

**Why this matters for this lab:** the blocklist only recognizes the 8
exact hashes of the real compromised intermediates. Any CA we generate
(even if rejected by everyone, even if totally unknown) **neither
triggers nor avoids** that code path — it's simply never recognized by
Dart/BoringSSL's own trust store, in either version. We confirmed this
in practice: running the Flutter app against the test CA generated by
`generate-ca.sh`, without installing anything on the OS, **the
vulnerable version (3.47.7) already rejects it** — because the cause of
rejection there is "CA unknown to Dart", not "CA passed the blocklist".
That's consistent and expected; it's not a failed test. Only after
installing the test CA in the OS trust store (`trust-ca-linux.sh`)
does the connection start succeeding — simulating "someone decided to
trust this CA".

**What this deliberately leaves out of reach:** reproducing the literal
exploitation of the CVE would require signing a forged certificate with
the private key of one of the 8 real intermediates. Public research
indicates those keys were generated with weak entropy and were recovered
by researchers — meaning they could technically be used to forge
certificates chaining up to a genuinely, publicly trusted root. This lab
**does not seek, reproduce, or use** that material: doing so would stop
being a contained lab and would become a real tool for intercepting
third-party HTTPS traffic.

**What this lab demonstrates, with real evidence:** that `dart:io`
validates certificates with a trust store entirely its own and
independent of the operating system — the structural root cause behind
the advisory, even though the specific 8-SPKI blocklist isn't
reproducible here via live MITM.

## Binary forensic verification of the blocklist (definitive proof, no MITM)

Instead of trying to reproduce the exploitation live (which would
require the private key of a real compromised CA — off the table, see
above), we confirmed the blocklist **directly in the compiled
binaries**, using only public data:

1. The 8 SHA-256 SPKI hashes from the real BoringSSL commit
   ([`dd68207`](https://boringssl.googlesource.com/boringssl/+/dd682072baab8029a83347e639d056c03e48d7e0))
   are **public** — the security patch itself publishes them, so anyone
   can detect the compromised CAs. It's detection data, equivalent to a
   malware hash in an antivirus blocklist: it gives no ability to forge
   any certificate (that would require the private key, which is never
   fetched or used here).
2. `verify-blocklist-binary.py` searches for those 32 bytes, as a raw
   byte sequence, inside the compiled `dart` binary of each SDK version.

**Result obtained in this lab:**
```
3.47.7 (Dart 3.13.5, vulnerable): 0/8 found
3.47.9 (Dart 3.13.7, fixed):      8/8 found, at contiguous
                                   32-byte offsets (554352,
                                   554384, 554416, ... — a C array)
```
This is **direct, definitive** confirmation: the real patch's
`kBlockList[8][32]` array is physically present in the fixed version's
binary and completely absent from the vulnerable one — no MITM, forged
CA, or private key needed.

To run it yourself:
```bash
python3 -I verify-blocklist-binary.py ~/fvm/versions/3.47.7/bin/cache/dart-sdk/bin/dart
python3 -I verify-blocklist-binary.py ~/fvm/versions/3.47.9/bin/cache/dart-sdk/bin/dart
```
(adjust the path if your fvm cache lives elsewhere — check with `fvm list`)

## Flow overview

```
┌─────────────┐      intercepts        ┌──────────────┐      forged chain          ┌───────────────┐
│ Flutter app  │ ───────────────────▶ │  mitmproxy    │ ─────────────────────────▶│ signed with     │
│ "Rate Today" │   HTTPS via proxy     │  (mitmdump +  │   leaf + intermediate.crt  │ intermediate-ca │
│ (3.47.7 or   │ ◀─────────────────── │  tamper_quote)│ ◀───────────────────────── │ (our "eMudhra") │
│  3.47.9)     │   tampered quote      │               │                            │                 │
└─────────────┘                       └──────────────┘                            └───────────────┘
                                                                                           ▲
                                                                     root-ca.crt installed  │
                                                                     in OS (trust anchor)   │
                                                                     later: removed ────────┘
```

- **root-ca**: represents a public CA still trusted (analogous to the
  real eMudhra root, which remains valid).
- **intermediate-ca**: represents the compromised/blocklisted
  intermediate. mitmproxy signs the forged certificates with its key.
- **tamper_quote.py**: mitmproxy addon that, besides intercepting, swaps
  the real quote for the forged value before delivering it to the app —
  this is what gives the test visible impact, not just "the connection
  went through".
- The real test is: does the OS trust the `root-ca`/`intermediate-ca`,
  and does the Flutter app, using **default** validation (no override),
  agree with that decision or not.

## Scripts, in order

| Script | What it does |
|---|---|
| `generate-ca.sh` | Generates `root-ca`, `intermediate-ca`, and `mitmproxy-ca.pem` in `certs/` (gitignored) |
| `setup-mitmproxy.sh [port]` | Installs mitmproxy if needed, starts `mitmdump` using our CA to sign interceptions |
| `trust-ca-linux.sh` | Installs `root-ca.crt` in the Linux trust store (Debian/Ubuntu) |
| `untrust-ca-linux.sh` | Removes `root-ca.crt` from the Linux trust store |
| `verify-blocklist-binary.py` | Forensic check: searches the real blocklist's 8 public SHA-256 SPKI hashes inside the compiled `dart` binary of each version. Usage: `python3 -I verify-blocklist-binary.py <path-to-dart-binary>` |
| `run-attack-demo.sh [port]` | The real attack: starts mitmproxy with `addons/tamper_quote.py`, which tampers with the real quote before delivering it to the app |

Read each script's header before running it — they alter the system
trust store (with `sudo`), which is reversible, but it's worth knowing
what's happening.

## Full walkthrough

### 1. Generate the test CA
```bash
./generate-ca.sh
```

### 2. Start mitmproxy
```bash
./setup-mitmproxy.sh 8080
```
Leave it running in a separate terminal.

### 3. Route test traffic through the proxy
```bash
export http_proxy=http://127.0.0.1:8080
export https_proxy=http://127.0.0.1:8080
```

### 4. Trust the test CA on the OS
```bash
./trust-ca-linux.sh
```
Quick sanity check:
```bash
curl -v -x 127.0.0.1:8080 https://economia.awesomeapi.com.br/last/USD-BRL
```
Expected: `curl` connects without a certificate error — confirms the CA
is trusted and mitmproxy is forging correctly.

### 5. Run the real attack
```bash
./run-attack-demo.sh 8080
```
Leave it running in a separate terminal — this is `setup-mitmproxy.sh`
with the `tamper_quote.py` addon loaded, which swaps the real quote for
`R$ 1,00` before delivering it to the app.

### 6. Run the Flutter app on both versions
From the target project (`../tls_mitm_poc`, this folder's sibling):
```bash
cd ../tls_mitm_poc
fvm use 3.47.7 --force   # vulnerable version (Dart 3.13.5)
fvm flutter run
```
- **Expected (vulnerable):** all 3 tabs of "Rate Today" show the
  **forged** quote (`R$ 1.0000`), even with the CA distrusted on the OS.

Then:
```bash
fvm use 3.47.9 --force   # fixed version (Dart 3.13.7)
fvm flutter run
```
- **Expected (fixed):** the app fails to load any of the 3 tabs — the
  connection is rejected before the forged value ever arrives.

### 7. Clean up
```bash
./untrust-ca-linux.sh     # make sure the test CA is no longer trusted
unset http_proxy https_proxy
```
Stop `mitmdump` (Ctrl+C).

private keys and local dependencies — **must never be committed**
(already covered by this folder's `.gitignore`).
